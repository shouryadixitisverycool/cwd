Databases and Database Users

Chapters 1 & 2 of Elmasri & Navathe (7th ed.). Exercises 1.1, 1.2, 1.3, 1.8–1.12. Each topic below opens with its theory; the exercise topics give every assigned question with a full solution behind the Solution button. Questions marked must-do match past end-sem and quiz questions.

The story of this topic

A database is a collection of related data; a DBMS is the software that defines, builds and shares it. This part explains why we use a DBMS instead of plain files, using the small UNIVERSITY database as the running example. A database stores its own schema in a catalog, and that is what makes program–data independence possible.

What is inside

    1  What a database is

    Theory recap

    Data, database, miniworld

    Definition: Data and database

    Data are known facts that can be recorded and that have implicit meaning (names, phone numbers, grades, …). A database is a collection of related data.

    This definition is very general (a page of text is “related data”); common usage is narrower. A database has three implicit properties:

    1. It represents some aspect of the real world, called the miniworld or the universe of discourse (UoD). Changes to the miniworld are reflected in the database.
    2. It is a logically coherent collection of data with some inherent meaning. A random assortment of data is not a database.
    3. It is designed, built and populated for a specific purpose: it has an intended group of users and some preconceived applications that these users are interested in.

    A database therefore has a source of data, some interaction with real-world events (a customer buys a camera, an employee has a baby), and an audience actively interested in its contents. To stay accurate it must reflect miniworld changes as soon as possible.

    • Size and complexity vary: a few hundred address-book records; a library catalogue of half a million entries; Facebook (over a billion users) or Amazon (over 60 million active users, over 42 TB, hundreds of servers).
    • Manual or computerized: a library card catalogue is a manually maintained database. A computerized one may be maintained by custom application programs or by a DBMS.

    DBMS and database system

    Definition: Database management system (DBMS)

    A computerized, general-purpose software system that enables users to create and maintain a database. It facilitates defining, constructing, manipulating and sharing databases among various users and applications.

    FunctionMeaning
    DefiningSpecify the data types, structures and constraints of the data. The definition is stored by the DBMS as the database catalog (or dictionary); this descriptive information is called meta-data.
    ConstructingStoring the data on some storage medium controlled by the DBMS.
    ManipulatingQuerying (retrieve specific data), updating (reflect miniworld changes), generating reports.
    SharingLetting multiple users and programs access the database simultaneously.
    ProtectingSystem protection against hardware/software crashes, and security protection against unauthorized or malicious access.
    MaintainingLetting the system evolve over a life cycle of many years as requirements change.

    An application program accesses the database by sending queries or requests to the DBMS. A query typically causes data to be retrieved; a transaction may cause some data to be read and some data to be written.

    Definition: Database system

    The database together with the DBMS software (and, by extension, the application programs) is called a database system.

    A general-purpose DBMS is not mandatory: one can write a customized set of programs, in effect a special-purpose DBMS for one application (for example airline reservations). Either way, complex software is involved.

    Key idea

    Three distinct things: the database (the data, plus its stored definition), the DBMS (general-purpose software), and the database system (database + DBMS together).

    Where the database sits: the information system and design phases

    An organization’s IT department maintains an information system (computers, storage, application software, databases). Designing a new database (or a new application on an existing one) goes through:

    1. Requirements specification and analysis: requirements are documented in detail;
    2. Conceptual design: requirements are turned into a conceptual design (e.g. an ER schema, Chapter 3) that tools can maintain and transform;
    3. Logical design: translated into the data model of a commercial DBMS (e.g. relational);
    4. Physical design: specifications for storing and accessing the database.

    The design is then implemented, populated with data, and continuously maintained to mirror the miniworld.

    3  Characteristics of the database approach

    Theory recap

    In traditional file processing each user (application) defines and implements the files it needs as part of programming the application. Example: the grade-reporting office keeps files on students and grades and programs to print transcripts; the accounting office keeps its own student files for fees and payments. Both hold data about students, so storage is wasted and effort is duplicated to keep common data up to date.

    In the database approach a single repository holds data that is defined once and then accessed by many users through queries, transactions and application programs. Four characteristics distinguish it:

    Self-describing nature of a database system

    The database system contains the data and a complete definition (description) of the database structure and constraints, stored in the DBMS catalog as meta-data (structure of each file, type and storage format of each data item, constraints). Because a general-purpose DBMS is not written for one application, it reads the catalog to learn the structure of the files of any database (university, bank, company). In file processing the data definition is part of the program itself (e.g. C++ structs), so a program works with only one specific database. Some NOSQL systems store self-describing data (item names stored with the values) and need no separate meta-data.

    Insulation between programs and data, and data abstraction

    • Program-data independence: the structure of data files is stored in the catalog, separately from the access programs, so changing a file’s structure usually needs no program change. Example: adding Birth_date to STUDENT only changes the catalog entry; a file-processing program hard-coded to the record layout of Figure 1.4 would break.
    • Program-operation independence (object / object-relational systems): an operation has an interface (name + argument types) and a separate implementation; the implementation can change without affecting programs that call the interface.
    • Data abstraction is the characteristic that allows both independences: the DBMS gives users a conceptual representation of data that hides storage details and operation implementations. A data model is the type of data abstraction used to give this conceptual representation (objects, properties, interrelationships rather than bytes and offsets).

    Sharing of data and multiuser transaction processing

    A multiuser DBMS lets many users access the database at the same time. It needs concurrency control so concurrent updates give correct results (e.g. two airline agents must not assign the same seat). Such applications are online transaction processing (OLTP) applications. A transaction is an executing program or process that includes one or more database accesses (reads or updates). The DBMS enforces properties such as isolation (each transaction appears to run alone) and atomicity (all of a transaction’s operations happen, or none do).

    5  Advantages of using the DBMS approach

    Theory recap

    These capabilities are in addition to the four characteristics of Section 3 (book Section 1.3).

    Controlling redundancy

    In file processing each group keeps its own files (registration office and accounting office both keep student data). Storing the same data many times causes: (i) duplication of effort (one logical update, e.g. a new student, done once per file); (ii) wasted storage; (iii) inconsistency (an update applied to some files but not others, or entered differently, e.g. ‘JAN-19-1988’ vs. ‘JAN-29-1988’).

    Ideally each logical data item is stored in one place: this is data normalization. In practice controlled redundancy (denormalization) is sometimes used for performance, e.g. storing Student_name and Course_number in GRADE_REPORT (Figure 1.6(a)). The DBMS must then control it by automatic checks:

    • each (Student_name, Student_number) pair in GRADE_REPORT must match a STUDENT record;
    • each (Section_identifier, Course_number) pair in GRADE_REPORT must match a SECTION record.

    Restricting unauthorized access

    Not every user may see everything (salaries, bonuses), and some may only retrieve while others may update. The DBMS provides a security and authorization subsystem: the DBA creates accounts (with passwords) and specifies restrictions, which the DBMS enforces automatically. Privileged software (e.g. creating accounts) is limited to the DBA staff; parametric users may be limited to their canned transactions.

    Providing persistent storage for program objects

    Programming-language objects vanish when the program ends unless explicitly saved (with format conversions). Object-oriented DBMSs store complex objects (e.g. C++/Java objects) directly; such an object is persistent, since it survives program termination and can be retrieved later by another program. Traditional DBMSs suffered from the impedance mismatch problem (DBMS data structures incompatible with the language’s structures).

    Storage structures and search techniques for efficient query processing

    Data is on disk, so the DBMS provides indexes (tree- or hash-based auxiliary files), its own buffering/caching module (keeps parts of the database in main memory), and a query processing and optimization module that chooses an efficient execution plan. Choosing indexes is part of physical design and tuning, a DBA responsibility.

    Providing backup and recovery

    The backup and recovery subsystem handles hardware/software failures: if the system fails in the middle of a complex update transaction, the database is restored to its state before the transaction began. Disk backup protects against catastrophic disk failure.

    Providing multiple user interfaces

    Apps for mobile users, query languages for casual users, programming-language interfaces for application programmers, forms and command codes for parametric users, menu-driven and natural-language interfaces for standalone users. Forms and menus are GUIs; Web-enabling a database is common.

    Representing complex relationships among data

    Brown’s STUDENT record relates to four GRADE_REPORT records; each SECTION record relates to one COURSE record and to many GRADE_REPORT records. The DBMS must represent varied relationships, define new ones as they arise, and retrieve/update related data efficiently.

    Enforcing integrity constraints

    • Data type / domain: Class is a one-digit integer, Name at most 30 alphabetic characters; restricting Class to 1–5 is an additional constraint.
    • Referential integrity: a record in one file must be related to records in another, e.g. every SECTION record must be related to a COURSE record.
    • Key (uniqueness) constraint: every COURSE record has a unique Course_number.
    • Business rules: constraints of large applications, some enforced by the DBMS, others checked by update programs or at data entry.
    • Inherent rules of a data model: rules implicit in the model itself (in the ER model a relationship must involve at least two entities).

    Constraints cannot catch every error: entering ‘C’ when the student earned ‘A’ is a valid value, so only a human notices; ‘Z’ would be rejected automatically as an invalid Grade.

    Permitting inferencing and actions using rules and triggers

    Deductive database systems define deduction rules to infer new information from stored facts (e.g. which students are on probation), declaratively, so changing the rule is easier than recoding programs. Relational systems offer triggers (rules activated by updates to a table that perform further operations) and stored procedures. Active database systems provide active rules that start actions automatically when events and conditions occur.

    Additional implications of the database approach

    • Enforcing standards (names and formats of data elements, report structures, terminology) by the DBA.
    • Reduced application development time: a new application (e.g. a new report) takes roughly one-sixth to one-fourth of the time it would with a file system, once the database is running.
    • Flexibility: the structure can evolve (add a file or data element) without affecting stored data and existing programs.
    • Availability of up-to-date information: one user’s update is immediately visible to all (made possible by concurrency control and recovery).
    • Economies of scale: consolidating data and applications reduces overlap and lets the organization buy more powerful shared equipment.
    Memory hook for the advantages list

    Redundancy control, Restricted access, Persistent objects, Indexing / query processing, Backup & recovery, Multiple interfaces, Complex relationships, Integrity constraints, Deduction / triggers; plus standards, development time, flexibility, up-to-date information, economies of scale.

    6  A brief history and today’s applications

    Theory recap
    EraKey points
    Hierarchical and network systems (mid-1960s to 1980s, mainframes)Large numbers of similar records. Main problem: conceptual relationships were intermixed with physical storage (a student’s grade records stored next to the student record), so little data abstraction and program-data independence; new queries hard to run efficiently; only programming-language interfaces. Three paradigms: hierarchical, network, inverted-file.
    Relational databases (late 1970s research, commercial early 1980s)Separate physical storage from conceptual representation; a mathematical foundation; high-level query languages. Slow at first (no physical pointers), then fast with new indexing and query optimization; became dominant.
    Object-oriented databases (1980s on)Complex structured objects, encapsulation, inheritance, object identity. Limited use (complexity, no early standard); OO concepts were absorbed into object-relational DBMSs (ORDBMSs).
    Web and XML (1990s on)E-commerce pages show data dynamically extracted from DBMSs; XML is a standard for interchanging data among databases and Web pages.
    New applicationsScientific data, images, video, data mining, spatial/GIS, time series. Plain relational systems needed more complex structures, new data types, new operations, new indexes, so vendors added extensions and modules.
    Big data and NOSQL (2000s on)Social media, Web search, cloud storage need fast search on huge, non-traditional data. NOSQL = “Not Only SQL”.

    Other applications named in the chapter: multimedia databases, GIS, data warehouses and OLAP for decision support, real-time and active databases for industrial control, database search techniques on the Web.

    7  When not to use a DBMS

    Theory recap

    Overhead costs of a DBMS: a high initial investment in hardware, software and training; the generality it provides for defining and processing data; and the overhead of security, concurrency control, recovery and integrity functions.

    Custom (file-based) applications may be better when:

    • the application is simple, well defined and not expected to change at all;
    • there are stringent real-time requirements the DBMS overhead might miss;
    • it is an embedded system with limited storage, where a general-purpose DBMS would not fit;
    • there is no multiple-user access to the data.

    Examples: CAD tools with proprietary file managers for drawings and 3D objects; telephone switching systems (fast, hierarchically organized data for call routing); GIS implementations with their own map data structures.

    1.2Four main types of actionsE&N Ex. 1.2 · p. 28

    What four main types of actions involve databases? Briefly discuss each.

    Solution · written for this guide

    The four actions are the functions a DBMS supports on a database:

    1. Defining the database: specifying the data types, structures and constraints of the data to be stored. The definition is stored in the catalog as meta-data. Example: STUDENT has Name (string of up to 30 letters), Student_number, Class (integer 1–5) and Major.
    2. Constructing the database: storing the data itself on a storage medium controlled by the DBMS (loading the initial records). Example: inserting the records for Smith and Brown.
    3. Manipulating the database: querying it to retrieve specific data, updating it to reflect changes in the miniworld, and generating reports. Example: “list Smith’s transcript”; “change Smith’s class to 2”.
    4. Sharing the database: allowing multiple users and programs to access it simultaneously, with concurrency control so that concurrent updates stay correct. Example: registrar and accounts office both using STUDENT at the same time.
    Answer

    Defining, constructing, manipulating and sharing (the DBMS additionally protects the database and maintains it as requirements evolve).

    1.3Database approach vs. file systemsE&N Ex. 1.3 · p. 28

    Discuss the main characteristics of the database approach and how it differs from traditional file systems.

    Solution · written for this guide

    In traditional file processing each user group defines and implements its own files as part of its application programs (the grade office and the accounting office each keep a student file). In the database approach a single repository holds data that is defined once and is accessed by many users. The four characteristics:

    1. Self-describing nature

    The database system holds the data and its complete description (structure, types, formats, constraints) in the catalog (meta-data). The general-purpose DBMS reads the catalog to work with any database. File systems: the data definition is coded inside each program (e.g. a C++ struct), so a program works only with its own files.

    2. Insulation between programs and data; data abstraction

    Program-data independence: file structure lives in the catalog, so adding Birth_date to STUDENT only changes the catalog; programs are unchanged. Program-operation independence: operation interfaces are separate from their implementations (OO systems). Data abstraction: users see a conceptual representation (a data model) without storage details such as byte offsets (Figure 1.4). File systems: the record layout is embedded in every program, so a structure change means changing every program that accesses the file.

    3. Multiple views

    Each user group can have its own view: a subset or derived (virtual) data, e.g. TRANSCRIPT and COURSE_PREREQUISITES. File systems: each application sees only its own fixed files.

    4. Sharing and multiuser transaction processing

    Many users access the same data concurrently; concurrency control keeps updates correct (no two agents book the same seat); transactions have isolation and atomicity. File systems: files usually belong to one application; there is no general mechanism for concurrent, atomic multi-user updates.

    CharacteristicDatabase approachTraditional file system
    Data descriptionStored once in the catalogInside each program
    Structure changeCatalog only (program-data independence)Every program changes
    User perspectiveConceptual (data model), many viewsPhysical layout, one view per application
    RedundancySingle repository; redundancy controlledEach group duplicates data; inconsistency
    ConcurrencyConcurrency control, transactionsTypically none

    File systems also duplicate data across groups, which wastes storage, duplicates update effort and causes inconsistency. A DBMS avoids this or keeps the duplication under control.

    1.9Controlled vs. uncontrolled redundancyE&N Ex. 1.9 · p. 28★ Must-do

    What is the difference between controlled and uncontrolled redundancy? Illustrate with examples.

    Solution · written for this guide

    Definitions

    Redundancy means storing the same logical data item (e.g. a student’s name or birth date) more than once.

    • Uncontrolled redundancy: the copies are kept in separate files maintained independently (typically by different user groups in a file-processing environment), and nothing ensures the copies agree.
    • Controlled redundancy: duplication that the designers introduce deliberately (usually for query performance, i.e. denormalization) and that the DBMS keeps consistent by automatically checking or propagating updates.

    Example of uncontrolled redundancy

    The registration office keeps a student file (name, birth date, courses, grades) and the accounting office keeps its own student file (name, birth date, fees, payments). Problems:

    1. Duplication of effort: a single logical update (admit a new student) must be entered once per file.
    2. Wasted storage: the same data is stored repeatedly.
    3. Inconsistency: an update reaches one file but not the other, or the groups enter it differently (one enters the birth date as ‘JAN-19-1988’, the other correctly as ‘JAN-29-1988’).

    Example of controlled redundancy

    To avoid joining three files every time a grade is retrieved, the designer stores Student_name and Course_number redundantly in GRADE_REPORT (Figure 1.6(a)):

    Student_numberStudent_nameSection_identifierCourse_numberGrade
    17Smith112MATH2410B
    17Smith119CS1310C
    8Brown85MATH2410A
    8Brown92CS1310A
    8Brown102CS3320B
    8Brown135CS3380A

    The redundancy is controlled because the DBMS is told, at design time, to check on every update of GRADE_REPORT that

    • the (Student_number, Student_name) pair matches a (Student_number, Name) pair in STUDENT, and
    • the (Section_identifier, Course_number) pair matches a SECTION record.

    The record (17, Brown, 112, MATH2410, B) of Figure 1.6(b) would be rejected: STUDENT says student 17 is Smith. Without the check (uncontrolled), this inconsistent record would be accepted.

    Summary

    Uncontrolled redundancyControlled redundancy
    OriginAccidental: separate files per user groupDeliberate design decision (denormalization)
    PurposeNone (side effect of file processing)Faster queries (fewer files to search/join)
    ConsistencyNot enforced; copies drift apartEnforced automatically by the DBMS
    Typical settingTraditional file processingDBMS approach
    ExampleTwo offices’ separate student files with different birth datesStudent_name in GRADE_REPORT checked against STUDENT
    Answer

    Uncontrolled redundancy is duplication that nobody keeps consistent, causing duplicated effort, wasted space and inconsistent data. Controlled redundancy is duplication introduced on purpose (usually for performance) whose consistency the DBMS enforces, e.g. Student_name stored in GRADE_REPORT but checked against STUDENT. The ideal design stores each logical item once (normalization); redundancy is used only when it is controlled.

    What the grader checks

    Expect: both definitions, and the key distinction is who guarantees consistency (nobody vs. the DBMS). At least one example of each. The three problems of uncontrolled redundancy (effort, storage, inconsistency). Saying “controlled redundancy = no redundancy” is wrong: it is redundancy that is managed.

    1.12Integrity constraintsE&N Ex. 1.12 · p. 28

    Cite some examples of integrity constraints that you think can apply to the database shown in Figure 1.2.

    Solution · written for this guide

    1. Domain (data type) constraints

    • STUDENT.Class is an integer in {1, 2, 3, 4, 5} (freshman to graduate).
    • GRADE_REPORT.Grade ∈\in∈ {A, B, C, D, F, I}.
    • COURSE.Credit_hours is a positive integer (say 1–6).
    • Course_number and Prerequisite_number have the format XXXXNNNN (four letters, four digits).
    • SECTION.Semester ∈\in∈ {Fall, Spring, Summer}; Year is a valid two-digit year.
    • STUDENT.Major and COURSE.Department are valid department codes (Major_type enumeration).

    2. Key (uniqueness) constraints

    • Student_number is unique in STUDENT; Course_number unique in COURSE; Section_identifier unique in SECTION.
    • (Student_number, Section_identifier) is unique in GRADE_REPORT: one grade per student per section.
    • (Course_number, Prerequisite_number) is unique in PREREQUISITE.
    • Course_name is unique in COURSE (plausible: no two courses with the same title).

    3. Referential integrity constraints

    • GRADE_REPORT.Student_number must match an existing STUDENT.Student_number.
    • GRADE_REPORT.Section_identifier must match an existing SECTION.Section_identifier.
    • SECTION.Course_number must match an existing COURSE.Course_number (the book’s own example).
    • PREREQUISITE.Course_number and PREREQUISITE.Prerequisite_number must both match COURSE records.

    4. Required values (NOT NULL)

    Every identifying item above must have a value; a STUDENT must have a Name; a COURSE must have Credit_hours.

    5. Semantic constraints / business rules (usually checked by programs or triggers)

    • A course cannot be its own prerequisite, and prerequisite chains cannot be cyclic.
    • A student may receive a grade in a section of a course only after completing all its prerequisites in an earlier term. (Figure 1.2 satisfies this: Brown took CS3320 in Spring 08 after CS1310 in Fall 07, and CS3380 in Fall 08 after CS3320 and MATH2410.)
    • The letter prefix of Course_number equals the offering Department (CS3380 is offered by CS).
    • A student may not be graded twice for the same course in the same term.
    • If redundancy is introduced as in Figure 1.6(a), Student_name in GRADE_REPORT must equal the Name in STUDENT for that Student_number.
    What the grader checks

    Graders look for variety: at least one domain, one key, one referential constraint, each tied to concrete columns of Figure 1.2, plus some business rule. Naming the constraint type for each example is what separates a full-marks answer from a list.

    11  Exam cheat sheet

    What a database is

    • Data: known facts that can be recorded and have implicit meaning (names, grades).
    • Database: a collection of related data with three implicit properties: (1) represents a miniworld / universe of discourse (UoD), and miniworld changes are reflected; (2) logically coherent, with inherent meaning (a random assortment is not a database); (3) designed, built and populated for a purpose: intended users and applications. May be manual (card catalogue).
    • DBMS: general-purpose software to define, construct, manipulate, share; also protects (system: crashes; security: unauthorized access) and maintains (evolves over years).
    • Define: types, structures, constraints; stored in the catalog as meta-data. Construct: store the data on a DBMS-controlled medium. Manipulate: query, update, report. Share: many users and programs at once.
    • Database system = database + DBMS (+ apps). A query retrieves; a transaction may read and write.

    The UNIVERSITY database (Fig. 1.2)

    • Five files: STUDENT(Name, Student_number, Class, Major); COURSE(Course_name, Course_number, Credit_hours, Department); SECTION(Section_identifier, Course_number, Semester, Year, Instructor); GRADE_REPORT(Student_number, Section_identifier, Grade); PREREQUISITE(Course_number, Prerequisite_number).
    • Data: Smith (17, Class 1, CS), Brown (8, Class 2, CS). CS3380 Database needs CS3320 and MATH2410; CS3320 needs CS1310. Class codes 1–5 (freshman..graduate).
    • Records are related by matching values: STUDENT–GRADE_REPORT, SECTION–GRADE_REPORT, COURSE–SECTION (all 1:N); COURSE–PREREQUISITE twice (as course, as prerequisite). Derived M:N: STUDENT–SECTION via GRADE_REPORT; recursive COURSE–COURSE via PREREQUISITE.
    • Catalog (Fig. 1.3): tables RELATIONS and COLUMNS describe the files as data (e.g. Course_number: XXXXNNNN).
    • Design phases: requirements specification and analysis →\to→ conceptual design (ER) →\to→ logical design (DBMS data model, e.g. relational) →\to→ physical design (storage, access).

    Characteristics of the database approach (vs. files)

    • File processing: each office defines its own files inside its programs (grades office and accounts both keep student data): wasted storage, duplicated effort. Database approach: one repository, defined once, used by many.
    • 1. Self-describing: the catalog holds the full definition (structure, types, formats, constraints) as meta-data, so one DBMS works with any database. Files: definition is inside the program (C++ struct). (Some NOSQL systems store self-describing data instead.)
    • 2. Insulation, data abstraction: program-data independence (structure in the catalog; adding Birth_date to STUDENT changes only the catalog); program-operation independence (OO: interface separate from implementation); data abstraction hides storage (Fig. 1.4 byte offsets); a data model is the type of abstraction used.
    • 3. Multiple views: a view is a subset or virtual (derived, not stored) data, e.g. TRANSCRIPT, COURSE_PREREQUISITES.
    • 4. Sharing, multiuser transactions: concurrency control (no seat sold twice), OLTP; isolation (each transaction appears alone) and atomicity (all or nothing).

    DefinitionIn each programOnce, in catalog
    RedundancyUncontrolledAvoided or controlled

    The people involved

    • Actors on the scene (use the contents): DBA (authorizes access, coordinates and monitors use, acquires HW/SW; accountable for security breaches and poor response time); database designers (choose structures; build one view per user group, then integrate); end users; system analysts (requirements, specify canned transactions) and application programmers (implement, test, maintain them).
    • End users: casual (occasional, varied queries: managers); naive/parametric (largest group; canned transactions = pre-programmed, tested, run with parameters: tellers, reservation agents); sophisticated (build own apps: engineers, scientists, analysts); standalone (personal packages: finance software).
    • Workers behind the scene (not interested in contents): DBMS system designers and implementers; tool developers; operators and maintenance personnel.

    Advantages of the DBMS approach

    • Hook: R R P I B M C I D = Redundancy control, Restricted access, Persistent objects, Indexing/query processing, Backup/recovery, Multiple interfaces, Complex relationships, Integrity constraints, Deduction/triggers.
    • Uncontrolled redundancy: separate copies nobody keeps consistent ⇒\Rightarrow⇒ (i) duplicated effort, (ii) wasted storage, (iii) inconsistency (JAN-19-1988 vs. JAN-29-1988).
    • Normalization: store each logical item once. Controlled redundancy (denormalization): deliberate copies for performance, kept consistent by the DBMS: Student_name and Course_number in GRADE_REPORT (Fig. 1.6a), checked against STUDENT and SECTION; so (17, Brown, 112, …) is rejected (17 is Smith).
    • Restricting access: security and authorization subsystem; DBA creates accounts and restrictions.
    • Persistent objects: OODBMS stores C++/Java objects beyond program end (avoids impedance mismatch).
    • Efficient queries: indexes (tree/hash), buffering, query optimization. Backup/recovery: a failed transaction is undone to its start state. Interfaces: apps, query languages, forms, menus, GUIs, natural language. Complex relationships: Brown →\to→ 4 GRADE_REPORTs.
    • Integrity constraints: domain/type (Class integer; 1–5 is extra); referential (each SECTION related to a COURSE); key (unique Course_number); business rules; inherent model rules (ER: a relationship has ≥2\ge 2≥2 entities). Cannot catch a valid but wrong value (C entered for A); Z is rejected.
    • Rules and triggers: deductive DBs infer facts (students on probation); triggers and stored procedures; active DBs fire rules on events.
    • Other implications: enforcing standards; development time ≈16\approx\frac16≈61​–14\frac1441​ of file-based; flexibility; up-to-date information for all; economies of scale.

    History and when not to use a DBMS

    • Eras: hierarchical/network (relationships mixed with storage) →\to→ relational (storage separate from concepts, high-level languages) →\to→ OO (absorbed into ORDBMS) →\to→ Web/XML →\to→ new apps →\to→ NOSQL (“Not Only SQL”).
    • DBMS overhead: initial investment (HW, SW, training); generality; security, concurrency, recovery, integrity costs.
    • Skip the DBMS when: simple, well-defined, unchanging app; stringent real-time needs; embedded system with little storage; no multiuser access. Examples: CAD file managers, telephone switching, custom GIS.

    Traps that cost marks

    • DBMS ≠\ne= database: DBMS is software; database + DBMS = database system.
    • Random data is not a database; a database need not be computerized.
    • Controlled redundancy is still redundancy: the difference is who guarantees consistency (nobody vs. the DBMS). Give one example of each and the three problems.
    • Bank tellers are naive/parametric, not sophisticated. Tool developers and operators are behind the scene.
    • Embedded, single-user, real-time is the classic “don’t use a DBMS” case.
    • Definitions need the defining property (database: related, coherent, purposeful; DBMS: general-purpose software that defines, constructs, manipulates, shares), not a synonym.

    Exam moves

    • Define + example: one Fig. 1.2 line per term lifts a definition to full marks.
    • File vs. DB: four characteristics, each with its file-system contrast, then a comparison table.
    • Constraints: name the type of each (domain, key, referential, NOT NULL, business rule) on real Fig. 1.2 columns.
    • Queries/updates: label retrieval / insert / delete / modify and the files touched. Relationships: linking attribute + 1:N, then the derived M:N.
